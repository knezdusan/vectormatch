# VectorMatch Blog Post Orchestrator — Session Prompt

This is the **initial prompt** to paste into a fresh Devin session to start the blog post publishing orchestrator. It gives the agent full context about the WordPress installation, the JSON schema it will parse, the WPVibe MCP tools it will use, and the end-to-end workflow from JSON file to published post.

**Accompanying files to attach (or reference in the session):**
- `docs/wordpress/BlogPostGenerationPrompt.md` — the JSON output contract and validation rules (Section 3 and Section 5 are critical).
- `docs/wordpress/wordpress-blog-research-brief.md` — design system, taxonomy, technical setup.

The orchestrator prompt below is self-contained and works even without attachments, but attaching the two files above gives the agent deeper reference material.

STEP 3 — ASSEMBLE THE WORDPRESS POST CONTENT
Build the final HTML for the WordPress post content (the_content). This is what goes into the REST API POST /wp/v2/posts as the "content" field. It renders inside single.php's <div class="prose"> wrapper.

CRITICAL STYLING RULE — USE THE THEME'S .vm-* COMPONENT CLASSES, NOT RAW TAILWIND UTILITIES.
The theme (theme.css) defines a dedicated, on-brand component system (.vm-tldr, .vm-cta, .vm-takeaways, .vm-faq, .vm-figure, .vm-author, .vm-lead) written as plain CSS so it renders reliably. Do NOT rely on ad-hoc Tailwind utility strings (text-lg, my-8, not-prose, card, space-y-2, etc.) for post chrome — on the live (compiled) site those utilities are NOT guaranteed to be present, and .not-prose does NOT fully reset the theme's prose rules. Use the semantic classes below exactly.

The assembled content structure (in order):

1. HERO SUBTITLE (lead paragraph)
   <p class="vm-lead">{hero.subtitle}</p>

2. TL;DR CALLOUT (the direct answer — this is the "TL;DR" low-friction feature)
   <div class="vm-tldr">
     <p class="vm-tldr-label"><svg viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2" stroke-linecap="round" stroke-linejoin="round" style="width:.9rem;height:.9rem;"><path d="M13 2 3 14h9l-1 8 10-12h-9l1-8z"/></svg>The short answer</p>
     <p>{hero.direct_answer}</p>
   </div>

3. HERO CTA (from the cta_blocks entry with id "hero")
   <div class="vm-cta">
     <p class="vm-cta-text">{a short 3-6 word prompt line, e.g. "Skip the black box entirely."}</p>
     <a href="{cta_url}" class="btn-brand">{cta_copy}</a>
   </div>

4. KEY TAKEAWAYS
   <div class="vm-takeaways">
     <p class="vm-h">What you'll learn</p>
     <ul>
       <li>{takeaway}</li>   ... for each takeaway (the green check bullet is drawn by CSS, do NOT add a ✓ span)
     </ul>
   </div>

5. CONTENT_HTML (with markers replaced)
   Take content_html and replace:
   - [[CTA:id]] → <div class="vm-cta"><p class="vm-cta-text">{short prompt line}</p><a href="{url}" class="btn-brand">{copy}</a></div>
   - [[IMAGE:id]] → <figure class="vm-figure"><img src="{uploaded_url}" alt="{alt_text}" /><figcaption>{caption}</figcaption></figure>
     (the .vm-figure class handles the border, radius, and caption styling — do NOT add utility classes to the <img>)
   Section headings in content_html MUST remain bare <h2> (no class attribute) — the theme uses these to auto-build the Table of Contents. Do NOT put class attributes on section <h2>s.
   The hero image is NOT inserted into the body — it is set as the WordPress featured image (see Step 5).

6. FAQ SECTION (after the body content) — rendered as an accessible accordion
   <section class="vm-faq">
     <p class="vm-h">Frequently asked questions</p>
     <details class="vm-faq-item"><summary>{question}</summary><div class="vm-faq-answer"><p>{answer}</p></div></details>
     ... for each FAQ entry
   </section>

7. CONCLUSION (after FAQ) — lead the conclusion with a bare <h2> so it appears in the TOC
   <h2>The bottom line</h2>
   {conclusion.summary_html}
   <div class="vm-cta"><p class="vm-cta-text">{short prompt line}</p><a href="{closing_cta_url}" class="btn-brand">{closing_cta_copy}</a></div>

8. AUTHOR BOX (after conclusion)
   <div class="vm-author">
     <div class="vm-author-badge">VM</div>
     <div>
       <p class="vm-author-name">{author_box.byline}</p>
       {author_box.html}
     </div>
   </div>

IMPORTANT STYLING NOTES:
- Use ONLY the .vm-* component classes and .btn-brand for post chrome. They are defined in theme.css and are the single source of truth for the blog's element design.
- Section <h2>s in the body must be bare (<h2>Heading</h2>) — no class, no id. The theme injects ids and builds the TOC automatically. Component headings use <p class="vm-h"> (NOT <h2>) so they never pollute the TOC.
- Do NOT add inline color/spacing styles. The only inline styles allowed are tiny SVG icon sizing (width/height) as shown above.
- CTA buttons always use class="btn-brand" (white text + gradient are enforced by the theme).
- Keep all HTML semantic and clean. No <script> tags. No inline JavaScript. No raw Tailwind utility classes on post content.

AUTOMATIC (THEME-LEVEL) FEATURES — the orchestrator does NOT inject these; single.php adds them for every post:
- Reading-time estimate (word count / 200) in the meta row.
- Category chip, date, author in the meta row.
- Table of contents (auto-built from bare section <h2>s; shown when there are >= 3 sections).
- Reading-progress bar at the top of the viewport.
- Featured image rendering, tag list, and prev/next navigation.
So the orchestrator must NOT add its own reading time, TOC, meta row, or progress bar — just the content components above.

STEP 4 — HANDLE IMAGES
Image RELEVANCE matters more than image count. A generic, off-topic stock photo (a laptop on a desk, a couch, people shaking hands) looks worse than no image at all and cheapens the post. Prefer relevant, on-brand visuals; when none is realistically obtainable, prefer an inline SVG diagram or omit the inline image entirely.

Decision order for each inline image (role "inline"/"diagram"):

4a. If the image concept is a DIAGRAM, FLOW, COMPARISON, or PROCESS (most technical posts):
  - Do NOT use a stock photo. Build a clean inline SVG diagram in the VectorMatch palette
    (cards #2a2a35, purple #8b5cf6/#a855f7, emerald #34d399, text #f5f5f7/#a1a1aa on #16161e),
    using viewBox + style="width:100%;height:auto" so it is responsive.
  - Wrap it: <figure class="vm-figure vm-figure-diagram"><svg ...>...</svg><figcaption>{caption}</figcaption></figure>
  - This is the PREFERRED visual for ATS/engineering/market topics and needs no upload.

4b. If a real, RELEVANT photo genuinely fits (e.g. a person coding, an office) and the JSON has a
    verified candidate_url: fetch and upload via upload_media, then render as <figure class="vm-figure">.

4c. If no candidate_url, try search_images on Unsplash with suggested_search_query ONLY IF a photo
    would be genuinely relevant. Judge the results critically: if the top results are generic/off-topic,
    do NOT use them — fall back to 4a (SVG) or omit the image and remove its [[IMAGE:id]] marker.
    When you do use an Unsplash photo, add attribution to the caption: "Photo: {photographer} on Unsplash".

4d. HERO / FEATURED IMAGE (role "hero"):
  - Prefer a branded cover: if no strongly relevant photo exists, generate a branded SVG cover
    (dark gradient background with the post title + category, brand colors) and upload it as the featured image.
    A branded cover is on-brand and reads better in the blog index and social cards than a random stock photo.
  - Only use an Unsplash hero photo when it is clearly relevant to the topic.

4e. After uploading each image, record the WordPress media ID and URL:
  - Hero/featured image → set as featured_media (Step 6).
  - Inline images/SVGs → replace [[IMAGE:id]] markers in the assembled content.
  - If you dropped an image (no good option), remove its [[IMAGE:id]] marker and note it in the repair report.

NOTE ON HUMAN-IN-THE-LOOP: image sourcing is the one area that may occasionally need the user. If a post
genuinely needs a specific real screenshot/graphic that cannot be generated as an SVG or sourced relevantly,
publish with a branded SVG placeholder (never a broken image, never an off-topic stock photo) and list the
image in the repair report as "needs a real asset" so the user can swap it later without blocking publication.

STEP 5 — DETERMINE PUBLISH DATE (backdating)
To make the posting schedule look natural:
1. Query the most recent published post: GET /wp/v2/posts?per_page=1&status=publish&orderby=date&order=desc
2. Get its date (the "date" field, ISO format).
3. Calculate the new post date: previous date + random 2 or 3 days.
4. If no previous posts exist, use today's date minus 2-3 days.
5. Use this date for both "date" and "date_gmt" in the POST /wp/v2/posts request.
6. The time of day should be randomized between 09:00 and 17:00 in UTC.

STEP 6 — CREATE THE POST IN WORDPRESS
Use rest_api to POST /wp/v2/posts with this body:
{
  "title": "{meta.title}",
  "slug": "{meta.slug}",
  "content": "{assembled_html_from_step_3}",
  "excerpt": "{meta.meta_description or first 160 chars of hero.direct_answer}",
  "status": "draft",
  "date": "{calculated_date}",
  "date_gmt": "{calculated_date}",
  "categories": [category_id],
  "tags": [tag_id_1, tag_id_2, ...],
  "featured_media": hero_media_id
}

After creating the draft:
1. Record the post ID.
2. Set Rank Math SEO meta fields via rest_api or run_wp_cli:
   - rank_math_title → meta.seo_title
   - rank_math_description → meta.meta_description
   - rank_math_focus_keyword → meta.primary_keyword
   (Use run_wp_cli: wp post meta update {post_id} rank_math_title "{seo_title}" etc.)

STEP 7 — VERIFY THE DRAFT
1. Fetch the draft post HTML: get_page_html on the preview URL (https://vectormatch.dev/blog/?p={post_id}&preview=true).
2. Check that:
   - The title renders as H1.
   - The hero subtitle and direct answer appear.
   - The key takeaways box renders with the card styling.
   - All CTA buttons render with the gradient style (.btn-brand).
   - All inline images render with captions.
   - The FAQ section renders.
   - The conclusion and author box render.
   - No raw [[CTA:...]] or [[IMAGE:...]] markers remain.
   - No [reference:N] placeholders remain.
3. If any issue is found, fix it by updating the post content via rest_api PUT /wp/v2/posts/{post_id}.

STEP 8 — PUBLISH
1. Update the post status to publish:
   PUT /wp/v2/posts/{post_id} with body {"status": "publish"}
2. Flush rewrite rules: run_wp_cli "rewrite flush"
3. Purge LiteSpeed Cache: run_wp_cli "litespeed purge all" (or "wp cache flush" if LiteSpeed CLI is not available)
4. Verify the published post: get_page_html on https://vectormatch.dev/blog/{slug}/
5. Run audit_page on the published URL to check for performance/accessibility/SEO issues.

Then ask: "Post published successfully. Provide the next blog post JSON file path for the next iteration, or type 'done' to end the session."

## Notes for the User (not part of the prompt)

### How to run the orchestrator
1. Open a new Devin session.
2. (Optional) Attach `docs/wordpress/BlogPostGenerationPrompt.md` and `docs/wordpress/wordpress-blog-research-brief.md` for deeper context.
3. Paste the entire prompt above.
4. The agent will initialize, then ask for the first JSON file path.
5. Provide the path: `docs/wordpress/posts-json/workday-ranks-candidates-pipeline-stage.json` (or whichever post you want to publish first).
6. The agent will validate, repair, assemble, publish, and verify — then ask for the next file.

### Backdating logic
The orchestrator queries the most recent post and backdates each new post 2-3 days before it. For the first post, it uses today minus 2-3 days. This creates a natural-looking publishing cadence. The randomization (2 or 3 days, and time of day between 09:00-17:00 UTC) is done by the agent at runtime.

### Image handling
Relevance first. The orchestrator decides per image:
1. Diagram/flow/comparison concepts → build an on-brand inline **SVG** (no upload, always relevant).
2. A genuinely relevant photo with a verified URL → upload via `upload_media`.
3. Unsplash via `search_images` — only if a photo is truly relevant; generic results are rejected.
4. Hero/featured → a **branded SVG cover** (title + gradient) when no relevant photo exists.

Off-topic stock photos are never used (they were the weakest part of the first post). Anything that genuinely needs a real asset is published with a branded placeholder and flagged in the repair report — never a broken image, never a blocking stop.

### Styling approach — the `.vm-*` design system
The blog's element design now lives entirely in the theme (`theme.css`), as a set of plain-CSS component classes so it renders reliably regardless of Tailwind's runtime utility compilation. The orchestrator emits these semantic classes; it does **not** hand-roll Tailwind utility strings for post chrome.

| Component | Class | Notes |
|---|---|---|
| Lead sentence | `.vm-lead` | Larger muted intro line |
| TL;DR / short answer | `.vm-tldr` + `.vm-tldr-label` | Purple-bordered callout from `hero.direct_answer` |
| In-content CTA | `.vm-cta` + `.vm-cta-text` + `.btn-brand` | Gradient button, white text enforced |
| Key takeaways | `.vm-takeaways` + `.vm-h` + `<ul><li>` | CSS-drawn emerald check bullets |
| FAQ | `.vm-faq` + `<details class="vm-faq-item"><summary>` + `.vm-faq-answer` | Native accordion, FAQPage-friendly |
| Figures | `.vm-figure` (+ `.vm-figure-diagram` for SVGs) | Border, radius, centered caption |
| Author box | `.vm-author` + `.vm-author-badge` + `.vm-author-name` | Gradient "VM" badge |

Plus a dark-theme prose palette override in `theme.css` that sets the `--tw-prose-*` variables (headings, body, links, bold, code, quotes, tables) to the light-on-dark VectorMatch palette. **This override is what fixed the original bug** where the Tailwind Typography plugin's light-mode defaults made headings, inline links and bold text near-invisible on the dark background.

### Automatic (theme-level) features in single.php
These are added for every post automatically — the orchestrator must not duplicate them:
- **Reading time** (words / 200) in the meta row.
- **Meta row**: category chip · date · author · reading time.
- **Table of contents**, auto-built from bare section `<h2>`s (shown at ≥ 3 sections). Component headings use `<p class="vm-h">` so they never appear in the TOC.
- **Reading-progress bar** fixed at the top of the viewport.

### Why theme-native, not plugins (research summary)
For styling and the low-effort features (reading time, TOC, TL;DR, progress bar, FAQ accordion) I evaluated popular plugins (LuckyWP/Easy Table of Contents, Reading Time WP, Ultimate Blocks/Kadence for callouts & accordions, Yoast/Rank Math FAQ blocks). Decision: **implement natively in the theme.** Rationale:
- **Brand fidelity** — generic plugins ship their own light-mode CSS/JS that fights this bespoke dark Tailwind design system and would need heavy overriding anyway.
- **Performance** — the features are a few lines of PHP/CSS and one tiny inline script; plugins add extra CSS/JS bundles and DB options (against the LiteSpeed/Core-Web-Vitals goals in the blueprint).
- **Maintainability & consistency** — one source of truth (`theme.css` + `single.php`) that every post inherits, versioned with the theme, no plugin update/compatibility risk.
- **Already-present tools suffice** — Rank Math handles FAQ/Article schema and SEO; LiteSpeed handles caching. No new plugin is needed for the current scope.
Revisit a plugin only if we later need author-managed, editor-side rich blocks (e.g. non-technical staff composing posts in Gutenberg) rather than orchestrator-generated HTML.

### Iteration and refinement
After the first post is published, review:
- The rendered post at `https://vectormatch.dev/blog/{slug}/`.
- The audit report for performance/accessibility/SEO issues.
- The repair report for any data issues that were compensated.

Then refine as needed before running the next post. Because the element design now lives in `theme.css` (`.vm-*` classes) and `single.php`, most visual refinements are made once in the theme and instantly apply to every post — not per-post. Common refinement areas:
- `.vm-cta` / `.btn-brand` sizing, spacing, mobile behavior (theme.css).
- `.vm-tldr` / `.vm-takeaways` / `.vm-faq` padding, borders, backgrounds (theme.css).
- `.vm-figure` image sizing/alignment (theme.css).
- TOC / reading-time / progress-bar behavior (single.php).
- Rank Math FAQ/Article schema configuration.
