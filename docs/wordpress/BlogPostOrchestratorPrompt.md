# VectorMatch Blog Post Orchestrator — Session Prompt

This is the **initial prompt** to paste into a fresh Devin session to start the blog post publishing orchestrator. It gives the agent full context about the WordPress installation, the JSON schema it will parse, the WordPress REST API tools it will use, and the end-to-end workflow from JSON file to published post.

**Accompanying files to attach (or reference in the session):**
- `docs/wordpress/BlogPostGenerationPrompt.md` — the JSON output contract and validation rules (Section 3 and Section 5 are critical).
- `docs/wordpress/wordpress-blog-research-brief.md` — design system, taxonomy, technical setup.

The orchestrator prompt below is self-contained and works even without attachments, but attaching the two files above gives the agent deeper reference material.

---

You do this one post per session iteration.

WORKFLOW (per iteration)

STEP 0 — INITIALIZATION (first iteration only)
1. Verify the environment variables are set: WP_API_URL, WP_APP_USER, WP_APP_PASSWORD (and optionally UNSPLASH_ACCESS_KEY). If any required variable is missing, ask the user to provide it before proceeding.
2. Verify the REST API connection: GET /wp/v2/posts?per_page=1 with HTTP Basic Auth (WP_APP_USER:WP_APP_PASSWORD). A 200 response confirms the application password works and the API is reachable.
3. Fetch existing posts: GET /wp/v2/posts?per_page=50&orderby=date&order=desc to determine the most recent post date (for backdating).
4. If no posts exist yet, use today's date as the starting point.
5. Announce: "Orchestrator initialized. Ready for the first blog post JSON. Please provide the path to the JSON file."

STEP 1 — RECEIVE THE JSON FILE
Ask the user: "Please provide the path to the blog post JSON file for this iteration."
The file will be at: docs/wordpress/posts-json/<slug>.json
Read the file and parse it as JSON.

STEP 2 — VALIDATE AND REPAIR (compensate, do not reject)
Run through the validation checks below. For each failure, attempt to repair the data automatically. Only report a blocking error if repair is impossible AND the post cannot be published coherently without the missing data.

VALIDATION + REPAIR RULES:

2a. Top-level structure
- Required keys: meta, hero, key_takeaways, content_html, cta_blocks, images, faq, conclusion, author_box, research_appendix.
- Repair: if a key is missing, create a reasonable default (e.g., empty array for faq, default author_box for VectorMatch Team).

2b. meta.tags
- Check each tag against the approved tag list above.
- REPAIR: if a tag is a category name (e.g., "Job Search Strategy"), REMOVE it. If after removal fewer than 2 tags remain, add "Networking" or "Portfolio" as a sensible default based on the post topic.
- REPAIR: if a tag is a close variant (e.g., "Nextjs" instead of "Next.js"), correct it to the exact approved name.
- Never create new tags in WordPress — only use existing IDs.

2c. meta.category
- Must be one of the 6 approved categories. Map the name to the ID using the list above.
- REPAIR: if the category is missing or invalid, infer it from the topic/tags and use the best match.

2d. meta.seo_title (55-60 chars)
- REPAIR: if longer than 60, truncate at a word boundary. If shorter than 55, extend with a relevant keyword. If missing, derive from meta.title.

2e. meta.meta_description (135-160 chars)
- REPAIR: if longer than 160, truncate at a sentence/word boundary. If shorter than 135, extend with a benefit phrase from the hero.direct_answer. If missing, derive from hero.direct_answer.

2f. meta.slug
- REPAIR: if missing, derive from the title (lowercase, hyphenated, keyword-first). Ensure it matches the filename.

2g. hero.subtitle and hero.direct_answer
- REPAIR: if missing, derive a subtitle from key_takeaways[0] and a direct_answer from the first paragraph of content_html.

2h. content_html
- Check for [reference:N], [source:N], [1] style placeholders.
- REPAIR: replace each [reference:N] or [N] placeholder by removing it (the sources are in research_appendix). If the surrounding sentence references a source, add an inline link using the matching URL from research_appendix.sources if available.
- Check for <h1> tags — remove them (the title is rendered by single.php).
- Check that it starts with <h2>.
- Check H2 count is 3-5. If 6+, merge the last two sections. If fewer than 3, split the longest section.
- Check that each <h2> is followed by a <p> (after optional markers). If a direct-answer <p> is missing or too short, prepend a 40-50 word summary paragraph generated from the section content.
- Check internal links (min 2). REPAIR: if fewer than 2, add links to https://vectormatch.dev or /blog/<other-slug>/ for related posts.
- Check external links (min 2). REPAIR: if fewer than 2, convert relevant source mentions in research_appendix to inline <a href> links.

2i. cta_blocks
- Check buyer_drive is one of: save, gain, reduce, increase, improve.
- REPAIR: if a phrase like "reduce rejections" is used, extract the first word (reduce). If missing, default to "gain".
- Check copy ends with →. REPAIR: append → if missing.
- Check url is https://vectormatch.dev. REPAIR: set it if missing or wrong.

2j. images
- Check exactly one image has role "hero" and id "hero".
- REPAIR: if no hero image, create one from the first inline image's spec or generate a default hero spec (alt_text from meta.title, description "Hero image for the post", generation_prompt using brand colors).
- Check all role values are "hero", "inline", or "diagram".
- REPAIR: normalize any other value to "inline".
- Check that every [[IMAGE:id]] marker in content_html has a matching image entry.
- REPAIR: if a marker has no matching image, remove the marker. If an image has no marker, add a marker at a sensible location in the body.

2k. faq
- Check 3-5 entries, each answer 40-80 words.
- REPAIR: if fewer than 3, generate additional Q&A from the content. If answers are too short, expand them by adding a supporting sentence from the content. If too long, trim.

2l. conclusion
- Check closing_cta_id references a valid cta_blocks entry.
- REPAIR: if missing or invalid, set to "closing". If no "closing" CTA block exists, create one.

2m. research_appendix
- This is NOT published — it is for your reference only. No repair needed. Use it to find source URLs for inline link repair in step 2h.

After all repairs, output a brief REPAIR REPORT:
"Repairs applied: [list each repair with the field name and what was changed]. No blocking issues." or "BLOCKING: [describe what cannot be repaired and what data is needed]."

STEP 3 — ASSEMBLE THE WORDPRESS POST CONTENT
Build the final HTML for the WordPress post content (the_content). This is what goes into the REST API POST /wp/v2/posts as the "content" field. It renders inside single.php's <div class="prose"> wrapper.

CRITICAL STYLING RULE — USE THE THEME'S .vm-* COMPONENT CLASSES, NOT RAW TAILWIND UTILITIES.
The theme (theme.css) defines a dedicated, on-brand component system (.vm-tldr, .vm-cta, .vm-takeaways, .vm-faq, .vm-figure, .vm-author, .vm-lead) written as plain CSS so it renders reliably. Do NOT rely on ad-hoc Tailwind utility strings (text-lg, my-8, not-prose, card, space-y-2, etc.) for post chrome — on the live (compiled) site those utilities are NOT guaranteed to be present, and .not-prose does NOT fully reset the theme's prose rules. Use the semantic classes below exactly.

The assembled content structure (in order):

1. HERO SUBTITLE (lead paragraph)
   <p class="vm-lead">{hero.subtitle}</p>

2. TL;DR CALLOUT (the direct answer — this is the "TL;DR" low-friction feature)
   <div class="vm-tldr">
     <p class="vm-tldr-label"><svg viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2" stroke-linecap="round" stroke-linejoin="round" style="width:.9rem;height:.9rem;"><path d="M13 2 3 14h9l-1 8 10-12h-9l1-8z"/></svg>The short answer</p>
     <p>{hero.direct_answer}</p>
   </div>

3. HERO CTA (from the cta_blocks entry with id "hero")
   <div class="vm-cta">
     <p class="vm-cta-text">{a short 3-6 word prompt line, e.g. "Skip the black box entirely."}</p>
     <a href="{cta_url}" class="btn-brand">{cta_copy}</a>
   </div>

4. KEY TAKEAWAYS
   <div class="vm-takeaways">
     <p class="vm-h">What you'll learn</p>
     <ul>
       <li>{takeaway}</li>   ... for each takeaway (the green check bullet is drawn by CSS, do NOT add a ✓ span)
     </ul>
   </div>

5. CONTENT_HTML (with markers replaced)
   Take content_html and replace:
   - [[CTA:id]] → <div class="vm-cta"><p class="vm-cta-text">{short prompt line}</p><a href="{url}" class="btn-brand">{copy}</a></div>
   - [[IMAGE:id]] → <figure class="vm-figure"><img src="{uploaded_url}" alt="{alt_text}" /><figcaption>{caption}</figcaption></figure>
     (the .vm-figure class handles the border, radius, and caption styling — do NOT add utility classes to the <img>)
   Section headings in content_html MUST remain bare <h2> (no class attribute) — the theme uses these to auto-build the Table of Contents. Do NOT put class attributes on section <h2>s.
   The hero image is NOT inserted into the body — it is set as the WordPress featured image (see Step 5).

6. FAQ SECTION (after the body content) — rendered as an accessible accordion
   <section class="vm-faq">
     <p class="vm-h">Frequently asked questions</p>
     <details class="vm-faq-item"><summary>{question}</summary><div class="vm-faq-answer"><p>{answer}</p></div></details>
     ... for each FAQ entry
   </section>

7. CONCLUSION (after FAQ) — lead the conclusion with a bare <h2> so it appears in the TOC
   <h2>The bottom line</h2>
   {conclusion.summary_html}
   <div class="vm-cta"><p class="vm-cta-text">{short prompt line}</p><a href="{closing_cta_url}" class="btn-brand">{closing_cta_copy}</a></div>

8. AUTHOR BOX (after conclusion)
   <div class="vm-author">
     <div class="vm-author-badge">VM</div>
     <div>
       <p class="vm-author-name">{author_box.byline}</p>
       {author_box.html}
     </div>
   </div>

IMPORTANT STYLING NOTES:
- Use ONLY the .vm-* component classes and .btn-brand for post chrome. They are defined in theme.css and are the single source of truth for the blog's element design.
- Section <h2>s in the body must be bare (<h2>Heading</h2>) — no class, no id. The theme injects ids and builds the TOC automatically. Component headings use <p class="vm-h"> (NOT <h2>) so they never pollute the TOC.
- Do NOT add inline color/spacing styles. The only inline styles allowed are tiny SVG icon sizing (width/height) as shown above.
- CTA buttons always use class="btn-brand" (white text + gradient are enforced by the theme).
- Keep all HTML semantic and clean. No <script> tags. No inline JavaScript. No raw Tailwind utility classes on post content.

AUTOMATIC (THEME-LEVEL) FEATURES — the orchestrator does NOT inject these; single.php adds them for every post:
- Reading-time estimate (word count / 200) in the meta row.
- Category chip, date, author in the meta row.
- Table of contents (auto-built from bare section <h2>s; shown when there are >= 3 sections).
- Reading-progress bar at the top of the viewport.
- Featured image rendering, tag list, and prev/next navigation.
So the orchestrator must NOT add its own reading time, TOC, meta row, or progress bar — just the content components above.

STEP 4 — HANDLE IMAGES
Image RELEVANCE matters more than image count. A generic, off-topic stock photo (a laptop on a desk, a couch, people shaking hands) looks worse than no image at all and cheapens the post. Prefer relevant, on-brand visuals; when none is realistically obtainable, prefer an inline SVG diagram or omit the inline image entirely.

Decision order for each inline image (role "inline"/"diagram"):

4a. If the image concept is a DIAGRAM, FLOW, COMPARISON, or PROCESS (most technical posts):
  - Do NOT use a stock photo. Build a clean inline SVG diagram in the VectorMatch palette
    (cards #2a2a35, purple #8b5cf6/#a855f7, emerald #34d399, text #f5f5f7/#a1a1aa on #16161e),
    using viewBox + style="width:100%;height:auto" so it is responsive.
  - Wrap it: <figure class="vm-figure vm-figure-diagram"><svg ...>...</svg><figcaption>{caption}</figcaption></figure>
  - This is the PREFERRED visual for ATS/engineering/market topics and needs no upload.

4b. If a real, RELEVANT photo genuinely fits (e.g. a person coding, an office) and the JSON has a
    verified candidate_url: download the image and upload it via the `upload_image_to_wp` function
    in `docs/wordpress/lib/publish_post.py` (which POSTs to /wp/v2/media), then render as
    <figure class="vm-figure">.

4c. If no candidate_url, search Unsplash via the Unsplash API (https://api.unsplash.com/search/photos)
    using the image's `suggested_search_query` — but ONLY IF UNSPLASH_ACCESS_KEY is set and a photo
    would be genuinely relevant. The `search_unsplash` and `upload_image_to_wp` functions in
    publish_post.py handle the search, download, and upload to /wp/v2/media. Judge the results
    critically: if the top results are generic/off-topic, do NOT use them — fall back to 4a (SVG)
    or omit the image and remove its [[IMAGE:id]] marker. When you do use an Unsplash photo, add
    attribution to the caption: "Photo: {photographer} on Unsplash".

4d. HERO / FEATURED IMAGE (role "hero"):
  - PRIMARY: generate the hero with DALL-E 3. Use images[0].generation_prompt plus a brand-style prefix.
    The prefix must be: "Dark-mode technical illustration for a web developer blog. Deep charcoal background #16161e, purple accents #7c3aed and #8b5cf6, emerald accent #34d399. Minimalist flat style, no text, no logos, no readable words, no people, clean vector shapes. "
    Call the OpenAI Images API: model="dall-e-3", size="1792x1024", quality="standard", n=1, response_format="url".
    DALL-E returns a temporary public URL (valid ~60 minutes). Pass it immediately to `upload_image_to_wp`
    (in publish_post.py) which downloads the image and uploads it to /wp/v2/media.
  - FALLBACK: if DALL-E is unavailable, the prompt is rejected by the content policy, or the generated image is off-brand, search Unsplash via the Unsplash API with images[0].suggested_search_query and upload the best match via `upload_image_to_wp`. Only use a photo when it is clearly relevant; otherwise fall back to a branded SVG cover.
  - Upload: call `upload_image_to_wp(image_url, post_title, alt_text)` from publish_post.py. Capture the returned attachment_id as hero_media_id for Step 6.
  - THEME DEPENDENCY: the current theme's single.php must call the_post_thumbnail() for the featured image to display. If the front-end still shows a placeholder, apply the single.php snippet in the repo docs or ask the user for the theme file.

4e. After uploading each image, record the WordPress media ID and URL:
  - Hero/featured image → set as featured_media (Step 6).
  - Inline images/SVGs → replace [[IMAGE:id]] markers in the assembled content.
  - If you dropped an image (no good option), remove its [[IMAGE:id]] marker and note it in the repair report.

NOTE ON HUMAN-IN-THE-LOOP: image sourcing is the one area that may occasionally need the user. If a post
genuinely needs a specific real screenshot/graphic that cannot be generated as an SVG or sourced relevantly,
publish with a branded SVG placeholder (never a broken image, never an off-topic stock photo) and list the
image in the repair report as "needs a real asset" so the user can swap it later without blocking publication.

STEP 5 — DETERMINE PUBLISH DATE (backdating — CRITICAL, DO NOT SKIP)
The blog is published in batches (multiple posts per session), but the dates must look like a natural
single-author cadence with 2-3 days between each post. Every new post must be dated 2 or 3 days
BEFORE the most recent existing post (i.e. further back in time, not forward).

ALGORITHM (follow exactly):
1. Query the most recent published post:
   GET /wp/v2/posts?per_page=1&status=publish&orderby=date&order=desc
2. Read its "date" field (ISO 8601 format, e.g. "2026-07-22T14:00:00").
3. Subtract a random interval of 2 OR 3 days from that date to get the new post date.
   - Example: if the most recent post is dated 2026-07-22T14:00:00, the new post should be
     dated either 2026-07-20T{HH}:00:00 (2 days before) or 2026-07-19T{HH}:00:00 (3 days before).
   - The 2-or-3-day choice must be randomized per post — do not always pick 2 or always pick 3.
4. If no previous posts exist, use today's date minus 2-3 days as the starting point.
5. Randomize the time of day between 09:00 and 17:00 UTC (whole hours, e.g. 09:00, 10:00, ... 17:00).
   Do NOT reuse the same time as the previous post.
6. Use the calculated date for BOTH "date" and "date_gmt" fields in the POST /wp/v2/posts request.
7. If publishing multiple posts in one session, re-query the most recent post date BEFORE each post
   (or track the date you just assigned and subtract another 2-3 days from it for the next post).
   Each post in the batch must be 2-3 days older than the one before it.

EXAMPLE — publishing 3 posts in one session when the most recent existing post is 2026-07-22T14:00:00:
  Post 1: 2026-07-20T11:00:00  (2 days before 07-22)
  Post 2: 2026-07-17T15:00:00  (3 days before 07-20)
  Post 3: 2026-07-15T09:00:00  (2 days before 07-17)

IMPORTANT: The publish_post.py script accepts an optional --date argument. Always pass the calculated
date when running the script:
  python3 docs/wordpress/lib/publish_post.py <post.json> --date "2026-07-20T11:00:00"
If --date is not provided, the script defaults to today's date — this should only happen for the
very first post. For all subsequent posts, ALWAYS pass --date.

STEP 6 — CREATE THE POST IN WORDPRESS
The primary path is to run the publishing script, which handles post creation, image upload,
SEO meta, and featured-image assignment in one step:
  python3 docs/wordpress/lib/publish_post.py <post.json>

If you need to create the post manually (e.g. for a repaired/assembled JSON that differs from
the original file), use `curl` or `requests` to POST /wp/v2/posts with HTTP Basic Auth
(WP_APP_USER:WP_APP_PASSWORD) and this body:
{
  "title": "{meta.title}",
  "slug": "{meta.slug}",
  "content": "{assembled_html_from_step_3}",
  "excerpt": "{meta.meta_description or first 160 chars of hero.direct_answer}",
  "status": "draft",
  "date": "{calculated_date}",
  "date_gmt": "{calculated_date}",
  "categories": [category_id],
  "tags": [tag_id_1, tag_id_2, ...],
  "featured_media": hero_media_id
}

After creating the draft:
1. Record the post ID.
2. Set Rank Math SEO meta fields. The publish_post.py script does this automatically; if you
   created the post manually, set them via the REST API or WP-CLI:
   - rank_math_title → meta.seo_title
   - rank_math_description → meta.meta_description
   - rank_math_focus_keyword → meta.primary_keyword
   (e.g. via WP-CLI: wp post meta update {post_id} rank_math_title "{seo_title}" etc.,
    or via a POST to /wp/v2/posts/{post_id} with the meta fields.)

STEP 7 — VERIFY THE DRAFT
1. Fetch the draft post HTML: use `webfetch` on the preview URL (https://vectormatch.dev/blog/?p={post_id}&preview=true).
2. Check that:
   - The title renders as H1.
   - The hero/featured image renders (requires single.php to call the_post_thumbnail()).
   - The hero subtitle and direct answer appear.
   - The key takeaways box renders with the card styling.
   - All CTA buttons render with the gradient style (.btn-brand).
   - All inline images render with captions.
   - The FAQ section renders.
   - The conclusion and author box render.
   - No raw [[CTA:...]] or [[IMAGE:...]] markers remain.
   - No [reference:N] placeholders remain.
3. If any issue is found, fix it by updating the post content via a PUT to /wp/v2/posts/{post_id}.

STEP 8 — PUBLISH
1. Update the post status to publish:
   PUT /wp/v2/posts/{post_id} with body {"status": "publish"} (via curl/requests with Basic Auth).
   Note: if you ran publish_post.py, you can pass a flag or edit the JSON to set status to "publish"
   directly; otherwise update the draft after verification.
2. Flush rewrite rules: run `wp rewrite flush` via WP-CLI (if available) or let WordPress handle it on publish.
3. Purge LiteSpeed Cache: run `wp litespeed purge all` via WP-CLI (or `wp cache flush` if LiteSpeed CLI is not available). LiteSpeed also auto-purges on post status changes in most configurations.
4. Verify the published post: use `webfetch` on https://vectormatch.dev/blog/{slug}/
5. Check the published URL for obvious rendering issues (you can use webfetch to inspect the HTML).

STEP 9 — REPORT
Output a structured report:

URL: https://vectormatch.dev/blog/{slug}/
Date: {published_date}
Category: {category_name} (ID {category_id})
Tags: {tag_names}
Featured image: {hero_image_url or "placeholder"}
Inline images: {count} uploaded, {count} placeholders
Repairs applied: {list or "none"}
SEO: seo_title={value}, meta_description={value}
Audit issues: {list or "none"}
═══════════════════════════════════════════════════════════════

Then ask: "Post published successfully. Provide the next blog post JSON file path for the next iteration, or type 'done' to end the session."

ISSUE ESCALATION PROTOCOL
═══════════════════════════════════════════════════════════════

1. CLASSIFY the issue:

### Backdating logic
The orchestrator queries the most recent published post and dates each new post 2 or 3 days BEFORE it (further back in time), with a randomized time of day between 09:00-17:00 UTC. For the first post ever, it uses today minus 2-3 days. When publishing multiple posts in one session, each subsequent post is dated 2-3 days before the previous one, creating a natural-looking reverse-chronological cadence. The `publish_post.py` script accepts `--date "YYYY-MM-DDTHH:00:00"` to set the date explicitly — this MUST be passed for every post except the very first one. The randomization (2 vs 3 days, and time of day) is done by the agent at runtime.

### Image handling
Relevance first. The orchestrator decides per image:
1. Diagram/flow/comparison concepts → build an on-brand inline **SVG** (no upload, always relevant).
2. A genuinely relevant photo with a verified URL → upload via `upload_image_to_wp` in `publish_post.py`.
3. Unsplash via the Unsplash API (UNSPLASH_ACCESS_KEY) — only if a photo is truly relevant; generic results are rejected.
4. Hero/featured → a **branded SVG cover** (title + gradient) when no relevant photo exists.

Off-topic stock photos are never used (they were the weakest part of the first post). Anything that genuinely needs a real asset is published with a branded placeholder and flagged in the repair report — never a broken image, never a blocking stop.

### Styling approach — the `.vm-*` design system
The blog's element design now lives entirely in the theme (`theme.css`), as a set of plain-CSS component classes so it renders reliably regardless of Tailwind's runtime utility compilation. The orchestrator emits these semantic classes; it does **not** hand-roll Tailwind utility strings for post chrome.

| Component | Class | Notes |
|---|---|---|
| Lead sentence | `.vm-lead` | Larger muted intro line |
| TL;DR / short answer | `.vm-tldr` + `.vm-tldr-label` | Purple-bordered callout from `hero.direct_answer` |
| In-content CTA | `.vm-cta` + `.vm-cta-text` + `.btn-brand` | Gradient button, white text enforced |
| Key takeaways | `.vm-takeaways` + `.vm-h` + `<ul><li>` | CSS-drawn emerald check bullets |
| FAQ | `.vm-faq` + `<details class="vm-faq-item"><summary>` + `.vm-faq-answer` | Native accordion, FAQPage-friendly |
| Figures | `.vm-figure` (+ `.vm-figure-diagram` for SVGs) | Border, radius, centered caption |
| Author box | `.vm-author` + `.vm-author-badge` + `.vm-author-name` | Gradient "VM" badge |

Plus a dark-theme prose palette override in `theme.css` that sets the `--tw-prose-*` variables (headings, body, links, bold, code, quotes, tables) to the light-on-dark VectorMatch palette. **This override is what fixed the original bug** where the Tailwind Typography plugin's light-mode defaults made headings, inline links and bold text near-invisible on the dark background.

### Automatic (theme-level) features in single.php
These are added for every post automatically — the orchestrator must not duplicate them:
- **Reading time** (words / 200) in the meta row.
- **Meta row**: category chip · date · author · reading time.
- **Table of contents**, auto-built from bare section `<h2>`s (shown at ≥ 3 sections). Component headings use `<p class="vm-h">` so they never appear in the TOC.
- **Reading-progress bar** fixed at the top of the viewport.

### Why theme-native, not plugins (research summary)
For styling and the low-effort features (reading time, TOC, TL;DR, progress bar, FAQ accordion) I evaluated popular plugins (LuckyWP/Easy Table of Contents, Reading Time WP, Ultimate Blocks/Kadence for callouts & accordions, Yoast/Rank Math FAQ blocks). Decision: **implement natively in the theme.** Rationale:
- **Brand fidelity** — generic plugins ship their own light-mode CSS/JS that fights this bespoke dark Tailwind design system and would need heavy overriding anyway.
- **Performance** — the features are a few lines of PHP/CSS and one tiny inline script; plugins add extra CSS/JS bundles and DB options (against the LiteSpeed/Core-Web-Vitals goals in the blueprint).
- **Maintainability & consistency** — one source of truth (`theme.css` + `single.php`) that every post inherits, versioned with the theme, no plugin update/compatibility risk.
- **Already-present tools suffice** — Rank Math handles FAQ/Article schema and SEO; LiteSpeed handles caching. No new plugin is needed for the current scope.
Revisit a plugin only if we later need author-managed, editor-side rich blocks (e.g. non-technical staff composing posts in Gutenberg) rather than orchestrator-generated HTML.
